# xlsx

A `.xlsx` is a ZIP of XML parts. Same packaging as
a `.docx`, plus one thing that causes most of its bugs: **a formula and its
value are stored separately.**

## The package

```
[Content_Types].xml      required
_rels/.rels               required
xl/workbook.xml          sheet names, references, defined names
xl/_rels/workbook.xml.rels  sheet relationships
xl/worksheets/sheet1.xml the cells
xl/sharedStrings.xml     strings referenced by index
xl/styles.xml            style indices — the reason styling is fragile
```

Sheet order comes from the workbook's relationship list, **not** from file names. A file
named `sheet1.xml` may be the third sheet. Read `workbook.xml` and follow the `r:id`s.

## Strings

Cell text is usually **not stored in the cell.** A cell holds an index into
`sharedStrings.xml`, with a type marker saying "this is a shared string." The literal
appears in `sharedStrings.xml` instead.

The consequence: reading a value means resolving the index, and writing one means either
reusing an existing entry or appending to the shared table. A tool that writes the literal
into the cell without updating the table produces a file that opens, and shows blanks or
numbers where text should be.

**Inline strings** also exist — text stored directly in the cell. Both forms are valid.
Readers handle both; writers should pick one and stay consistent.

## Formulas and cached values

A formula cell stores **two** things: the formula expression, and the value the last
calculation produced.

That cached value is what makes this dangerous. A file generated by a library contains a
formula and a cached value of **zero or empty**, because nothing evaluated it. Excel
recalculates on open and is fine. But anything reading the file programmatically —
pandas, a script, a previewer — sees the **cached value**, so it reads zeros.

There are two ways out, and both matter:

1. **Write the formula and clear the cached value**, forcing recalculation. Libraries
   differ in whether they offer this; setting `fullCalcOnLoad` in the workbook's
   calculation properties is the usual mechanism.
2. **Write the computed value** and no formula, when the value is all the consumer needs.

Which one is right depends entirely on who reads the file. A workbook for a human to
review should keep formulas visible. A workbook feeding a script should carry values.

**Dates are numbers with a number format.** A date is a serial number plus a cell style.
Write a Python `datetime` and it becomes a serial number with no date format and displays
as an integer. This is the most common "my dates are wrong" bug.

## Styling

Every cell carries an index into `styles.xml` — a `cellXfs` entry, which references
fonts, fills, borders, and number formats. Styles are **count-based**: position in the
list is the meaning.

So "make column C bold" means creating or finding a style at index *n* and pointing the
cell at *n*. Getting this wrong produces either wrong formatting or a corrupt file,
depending on whether the index exists. Libraries that append styles per cell will inflate
the file fast — thousands of near-identical entries — which is a size problem that looks
like a logic problem.

## Practical checks

* **Read values back with a raw reader, not just the library that wrote them.** Two tools
  disagreeing is how a shared-string bug surfaces.
* **Check the formulas are what you meant**, not just that the file opened.
* **Verify a date column renders as dates** — check the number format, not the value.
* **Conditional formatting and data validation live outside `sheet1.xml`** and are the
  first things a lossy round-trip drops.
* **Open in Excel before trusting it.** LibreOffice and Google Sheets are more forgiving,
  which means passing in one of them does not prove Excel is happy.
